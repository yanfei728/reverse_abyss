## 目标

保存、打开草稿、开发试玩均有异步阶段。旧请求回包不能改写另一张正在编辑的地图身份，不能覆盖请求发出之后的新改动，不能带着未保存内容离开编辑页。

## 实现约定

- 保存发起时捕获工作区身份（模型代次或等价令牌）、draftId、expectedRevision、完整内容快照/hash；仓库仍保存发起时快照，成功结果仍为现有 Result，不改变 JSON 格式或扩大存储系统。
- 保存回包时，只有仍处于同一工作区，才更新该工作区的 draftId/revision/保存状态。同图继续编辑允许保留 dirty；若已新建/导入/打开另一张图，旧保存可以完成，但不能把当前图绑定回旧草稿，不能改它的 dirty/历史/视角或声称当前图已保存。
- `openPlaytest` 的校验、保存与 handoff 必须针对同一份内容和同一工作区。保存期间发生编辑/切图时，留在编辑器，保留新工作并明确提示重试；也可在整个交接期间完整锁住有冲突的输入。不能用“先保存旧版本再把最新未保存版本带走”规避问题，不能自动无限循环保存。
- 打开草稿时，回包前若工作区/内容变化，取消这次过期替换并保留当前工作；若选择锁住编辑，须覆盖画布、键盘和切图入口，而不只禁用一个按钮。两个打开请求乱序返回时，旧请求不得覆盖更新的选择。
- 失败、取消、过期回包均不能清 dirty、丢历史或破坏草稿的 revision 绑定；正常保存/恢复、同图保存期间编辑仍可继续使用。
- 推荐用少量局部代次/快照核对解决，不引入框架、通用队列系统或重写编辑器。具体实现可由编码 agent 决定。

## 必要验证

用可控制 Promise 完成顺序的仓库做针对性行为回归，不只检查令牌/函数存在。若采用 UI 锁定方案，测试通过真实 UI 入口验证锁定有效；独立探针是问题复现参考，不要求为了原样运行探针而放弃合理实现。

1. 试玩自动保存期间编辑：要么编辑被完整阻止，要么保留新工作且不导航；成功导航时 handoff 的内容必须与已保存内容一致，并通过 play 校验。
2. 保存 A 期间打开/新建 B：旧回包不改变 B 的草稿绑定；随后保存 B 后 A 原内容仍在，B 有自己的正确草稿。用不同 id 的两张图验证。
3. 读取草稿期间编辑或切图：迟到回包不覆盖新工作。至少覆盖两个读取请求反向完成或等价的工作区切换。
4. 原普通保存/恢复、revision 冲突、写入失败、保存期间同图继续编辑、A3-C、连续跨层/暂停检查无新增失败。
